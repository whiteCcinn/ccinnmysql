# Security Policy

## Supported versions

Security fixes are released for the latest minor version of CcinnMysql.

| Version | Supported |
|---|---|
| 1.0.x | ✅ |

## Reporting a vulnerability

Please **do not open a public issue** for security problems.

Report vulnerabilities privately through GitHub's [private vulnerability reporting](https://github.com/whiteCcinn/ccinnmysql/security/advisories/new). Include:

- a description of the issue and its impact,
- steps to reproduce (server and version, connection options such as the TLS mode, sample data if relevant),
- any suggested fix.

You can expect an acknowledgement within a few days. Once a fix is available, we will publish a release and an advisory crediting the reporter (unless you prefer to remain anonymous).

## Scope and design notes

- Passwords, SSH secrets and client-certificate passphrases are stored in the macOS Keychain; saved profiles on disk never contain them.
- TLS is negotiated in place after the server greeting. *Preferred* (the default) encrypts when the server offers TLS but does not verify the certificate; it never retries in plaintext after a failed TLS handshake, and TLS 1.0/1.1 must be enabled per connection; use *Verify CA* or *Verify identity* (with your CA file) for servers you need to authenticate. Each connection has its own TLS session, so a session negotiated under a weaker mode is never resumed by a verifying one.
- `caching_sha2_password` / `sha256_password` full authentication sends the password only inside TLS, or encrypted with the server's RSA key. Retrieving that key over a plaintext connection is opt-in, because the key itself is not authenticated; pinning the key file avoids that.
- `mysql_clear_password` (LDAP / PAM) is only answered when explicitly enabled for a connection. `LOAD DATA LOCAL INFILE` is never offered to the server, and a server request for a local file is refused.
- SSH tunnels use the system `/usr/bin/ssh` with `StrictHostKeyChecking=accept-new` (changed host keys are rejected) and `ControlMaster=no` plus `ControlPath=none`, so a tunnel never becomes a shared connection that other sessions depend on, and never hands its port forward to a master connection you already run (which would keep the port open after the tunnel closes and skip the connection's own SSH authentication). Secrets reach `ssh` through a short-lived 0600 file, never the command line or environment.
- History and the MCP audit log redact credentials (`IDENTIFIED BY`, `PASSWORD(…)`, `SOURCE_PASSWORD`, …) and are written with mode 0600.
- The MCP server exposes only connections the user enabled, defaults to read-only, checks statements with the app's own lexer (which ends numbers where MySQL and MariaDB do, and refuses text that servers, sessions or other tools could read differently: executable comments, any backslash outside strings and quoted names (`\N` is NULL on MariaDB, which ends it after the N, and an error on MySQL 8), backslashes that move the end of a string under `NO_BACKSLASH_ESCAPES`, line comments other tools end early, a `;` left after `DELIMITER`, malformed literals) and additionally runs read-only calls inside `START TRANSACTION READ ONLY`; each call uses its own session, which is closed afterwards. Read-only calls run in the default reading of SQL (lexer-affecting `sql_mode`s such as `NO_BACKSLASH_ESCAPES`, `ANSI_QUOTES`, `ORACLE` and `PIPES_AS_CONCAT` are removed for the call), in `utf8mb4` (every connection is switched to it after the server's own setup, and it is re-checked before every read-only statement), and the check runs on the exact text sent; a call is refused when any of this cannot be ensured. Read-only tools refuse accounts that can reach server files, server state or other sessions' data through functions or views (`FILE`, `SUPER`, `PROCESS`, every dynamic privilege not reviewed as harmless such as `*_ADMIN` or `INNODB_REDO_LOG_ARCHIVE`, global `ALL PRIVILEGES`, `SELECT` on `*.*`, `mysql.*`, `performance_schema.*` or `sys.*`, also through a database pattern that matches one such as `%` or `m_sql`, and through roles; on MariaDB an account with nested roles can't be checked and is refused too) unless the user allows it per connection, and `run_query` never reads the `mysql`, `performance_schema` or `sys` schemas (names compared in any case), the `information_schema` views that show other sessions' statements, another session's plan (`EXPLAIN FOR CONNECTION`, MariaDB's `SHOW EXPLAIN` / `SHOW ANALYZE`), `SHOW REPLICA STATUS`, `SHOW BINLOG EVENTS` / `SHOW RELAYLOG EVENTS`, or account definitions (`SHOW GRANTS`, `SHOW CREATE USER`, which can print password hashes); tools that show other sessions' statements replace every literal with `?` (`get_replication_status` everything quoted in the last SQL error). Read-only calls may use only the reviewed built-in functions of the server's flavor; loadable, component and stored functions (qualified, back-quoted, or a built-in name with a space before `(` that the server resolves as a stored function) need the connection's allowance, and built-ins with side effects stay refused. Names reach the server as checked: read-only calls refuse names and `database` arguments holding a letter the servers fold to ASCII (the 19 letters such as ı, İ, ſ, K, ß, ﬁ), compare other names with the deny lists by an ASCII skeleton (case, compatibility forms and accents folded), and refuse MCP arguments with control characters; connections refuse a user or database name with NUL instead of dropping it, and so does the workbench's USE. Ways to make a read-only MCP call change data or schema, or read those, are considered vulnerabilities.
- "Read-only" means no data or schema changes. Stored functions, procedures and views defined with `SQL SECURITY DEFINER` (the default) run with their definer's privileges, which no check on the AI's account can see. This includes a definer-rights view that a privileged account (for example `root`) created over the process list: it shows every session's statements, with their values, to any account that may select from it, whether or not that account has `PROCESS`, so refusing privileged accounts does not cover it. This is an accepted risk: the app detects and reports those the account can reach whose definer is privileged or whose privileges it cannot see (Settings → MCP, and a notice with read-only results), and does not refuse them. Side effects inside stored functions that already exist on the server (for example `GET_LOCK`, `SLEEP`, or `KILL` where the server allows it) cannot be inspected by the app and are out of scope. For real isolation, connect MCP with a dedicated MySQL user that has only `SELECT` and `SHOW VIEW`; see the README's MCP section. The diagnostics tools need `PROCESS` (process list, InnoDB status) or `SELECT` on `performance_schema` (top statements), which make the account privileged, so they need the per-connection allowance. With it, the AI can see other sessions' statements, literals included, through existing invoker-rights views or routines over the process list or `performance_schema`, which the read-only check can't see into: this is the accepted risk of allowing such an account.
- Statements built by the app (metadata, `KILL`, row edits) quote identifiers and literals; issues that allow injecting SQL through object names or cell values are considered vulnerabilities.
- Update checks contact only `api.github.com` and `github.com`, send no personal data (the User-Agent is `CcinnMysql/<version>`), and run at most once a day unless you check manually. A downloaded disk image is accepted only from this repository's download URL for the same release tag, at the size the release lists, and with the SHA-256 published in that release's `SHA256SUMS.txt`. The checksum guards against corruption and truncation, not against a compromised GitHub release; authenticity relies on HTTPS to github.com. The app never replaces itself; you drag the new version into Applications.
